# Review 1 - based on __analysis/2_METADATA.md

## Source Analysis

`__analysis/2_METADATA.md` — K8s Labels and Annotations Passthrough

사용자가 `octovault-values.yaml`의 `metadata` 섹션에 `annotations`/`labels`를 지정하면,
OctoVault Controller가 생성하는 ConfigMap/Secret에 병합 적용하는 기능.

---

## What went well

- **Solution A 선택이 적절했다.** `valuesDoc` 구조체 확장 + 순수 함수 병합 방식은 최소 변경으로 요구사항을 충족했고, 테스트하기 쉬운 구조였다.
- **`mergeMap` 단일 헬퍼로 labels/annotations 공통 처리.** `mergeLabels`/`mergeAnnotations`가 같은 로직을 공유하여 중복이 없다.
- **예약 prefix 기반 필터링이 직관적이고 확장 가능하다.** `reservedPrefixes` 슬라이스에 항목만 추가하면 새로운 시스템 prefix를 보호할 수 있다.
- **업데이트 경로에서 labels/annotations를 항상 덮어쓰는 방식이 올바른 수렴 동작을 보장한다.** Reconcile마다 desired state로 수렴하며 stale 사용자 키가 자동 제거된다.
- **Red Task List가 구체적이어서 Yellow/Green 진행이 명확했다.** 태스크 그룹별 분리로 단계 커밋이 깔끔했다.

---

## Mistakes

### 1. Green 완료 후 dead code 미제거

`setManagedLabels` 함수는 Green phase에서 `applyConfigMap`/`applySecret`이 `sysLabels` 맵을 인라인 구성하면서 완전히 대체되었으나 제거되지 않고 남았다. `equalStringMap`, `equalBytesMap`도 업데이트 로직 단순화 후 호출처가 없어졌음에도 방치됐다.

**원인**: Green 단계에서 "최소 구현 통과"에 집중한 나머지 기존 코드와의 정합성 정리가 생략됐다.

### 2. 업데이트 경로 중복 구조 발생

labels/annotations 항상 갱신 정책을 추가할 때, 기존 `if !equalStringMap` 조건 블록을 제거하지 않고 바깥에 `return r.Update(ctx, &cm)`을 추가했다. 결과적으로 두 분기 모두 Update를 호출하는 이중 구조가 됐다.

```go
// 문제가 된 구조
if !equalStringMap(cm.Data, data) {
    // ...
    return r.Update(ctx, &cm)
}
return r.Update(ctx, &cm)  // 항상 Update
```

**원인**: 기존 로직을 건드리지 않으면서 새 동작을 추가하려는 보수적 접근이 중복을 낳았다.

### 3. Red Task List 체크박스 미업데이트

모든 태스크가 Green 완료 후에도 체크박스가 `[ ]`로 남아 있었다. 문서가 완료 상태를 반영하지 않아 추후 독자에게 혼동을 줄 수 있었다.

---

## Cautions

- **`cm.Data = data` 단순화는 맵 참조 공유에 주의가 필요하다.** `data`가 `applyOutput` 내부에서 선언된 로컬 맵이므로 현재 안전하지만, 나중에 `data` 맵을 재사용하거나 공유하는 구조로 바뀌면 `cm.Data`가 예기치 않게 변경될 수 있다. 방어적으로 쓰려면 `maps.Clone(data)`를 고려할 수 있다.
- **예약 prefix 필터링은 exact-prefix 매칭이다.** `octovault.it/foo` 형태는 막히지만 `xoctovault.it/foo`처럼 prefix를 우회하는 키는 통과한다. 현재 요구사항에서는 문제없지만, 향후 사용자 정의 prefix 허용 목록 기능이 추가된다면 이 점을 인지해야 한다.
- **`UserMetadata` Value Object는 도메인 모델에서 정의됐으나 구현되지 않았다.** Solution A 채택으로 불필요해졌지만, 도메인 모델 섹션에 해당 VO가 남아 있어 코드와 문서 간 불일치가 존재한다.

---

## Recommendations

### R1. Green 완료 체크리스트에 dead code 검토 항목 추가

Green 커밋 전, 새 구현으로 대체된 기존 함수/분기가 있는지 검토하는 단계를 추가한다. `go vet`과 함께 `staticcheck`나 `unused` 린터를 활용하면 자동 감지할 수 있다.

### R2. 업데이트 경로 설계 원칙 정립

"항상 덮어쓰기(always-overwrite)" 정책을 쓸 경우, 조건 분기 없이 desired state를 직접 할당 후 단일 Update 호출 패턴으로 통일한다:

```go
resource.Labels      = mergeLabels(sysLabels, userLabels)
resource.Annotations = mergeAnnotations(sysAnnotations, userAnnotations)
resource.Data        = data
return r.Update(ctx, &resource)
```

### R3. 분석 문서의 도메인 모델을 채택된 Solution과 일치시킨다

Solution A 채택으로 `UserMetadata` VO가 불필요해졌다면 도메인 모델 섹션에서 해당 내용을 제거하거나 "채택 안 됨" 표시를 한다. 코드와 문서의 정합성을 유지해야 이후 분석 시 혼동이 없다.

### R4. Red Task List 체크박스를 Green 커밋과 함께 업데이트한다

각 Green 커밋 시 해당 태스크 그룹의 체크박스를 `[x]`로 갱신하는 것을 커밋 전 체크 항목으로 삼는다.
