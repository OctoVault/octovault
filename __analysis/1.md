# Analysis 1 - 코드 리팩토링

## 기능 요구사항

현재 프로젝트(octovault-octovault)는 Kubernetes Operator로, GitHub 저장소에서 values.yaml을 가져와 ConfigMap 또는 Secret으로 동기화하며, AWS Secrets Manager / Parameter Store 와 연동하여 외부 시크릿을 주입하는 기능을 제공한다.

리팩토링 목표:
1. `octovault_controller.go` 파일의 과도한 크기(1057줄)와 책임 집중을 분리
2. 중복 코드 제거 (헬퍼 함수, 스킴 생성, 상태 비교 등)
3. 인터페이스 기반 추상화 일관성 확보
4. 테스트 가능성 향상 (HTTP 직접 호출 제거, 의존성 주입 일관화)
5. 패키지 구조를 도메인 중심으로 정리

## 도메인 모델

### Entities

1. **OctoVault** - GitHub 저장소의 values.yaml을 특정 네임스페이스의 ConfigMap/Secret으로 동기화하는 핵심 CR
   - Spec: OctoRepositoryRef, Repository, Path, GitRef, TargetName, TargetNamespace, PollInterval
   - Status: Phase, Message, Conditions, LastSyncedTime, ObservedRevision, AppliedDataHash, ResolvedType, ExternalRefs

2. **OctoRepository** - GitHub 조직/사용자와 인증 정보를 연결하는 클러스터 범위 CR
   - Spec: Organization, CredentialsRef
   - Status: Phase, Message, Conditions, SyncedSecretName, LastCheckedTime

3. **RepoSecret** - OctoRepository와 연결될 Kubernetes Secret (라벨 기반 관리)

### Value Objects

1. **NamespacedObjectRef** - 네임스페이스 + 이름으로 객체 참조
2. **LocalObjectRef** - 동일 네임스페이스 내 객체 참조 (이름만)
3. **ExternalRefStatus** - 외부 소스(AWS SM 등) 버전/스테이지 정보
4. **OutputType** - ConfigMap | Secret
5. **valuesDoc** - values.yaml 파싱 모델 (metadata.type + spec.data[])
6. **Meta** (awssm.Meta, awsps.Meta) - AWS 외부 소스 메타데이터

## Input / Output

### Input
- OctoVault CR (spec: repository, path, gitRef, targetName, targetNamespace, pollInterval)
- OctoRepository CR (spec: organization, credentialsRef)
- Kubernetes Secret (인증 토큰)
- GitHub API (values.yaml, schema.json, commit SHA)
- AWS Secrets Manager / Parameter Store (외부 시크릿 값)

### Output
- Kubernetes ConfigMap 또는 Secret (대상 네임스페이스에 생성/업데이트)
- CR Status 업데이트 (Phase, Conditions, Hash 등)
- Kubernetes Events (Synced, Failed 등)

## Related Functional Requirements

1. OctoVault Reconcile: values.yaml fetch → parse → validate → apply → status update
2. OctoRepository Reconcile: organization 접근 검증 → status update
3. RepoSecret Reconcile: 라벨이 있는 Secret 감시 → 이미 연결된 OctoRepository 확인
4. GitHub Content Fetching: REST API로 파일 내용/스키마/커밋 SHA 조회
5. AWS 시크릿 리졸브: AwsSecretManager, AwsParameterStore 타입 지원 + JSON 키 추출
6. Finalizer 기반 삭제 처리: OctoVault 삭제 시 대상 리소스에서 OwnerRef 제거

## Solutions

### S1. octovault_controller.go 파일 분리

현재 `octovault_controller.go`가 1057줄로, Reconciler + 유틸리티 + apply 로직 + 상태 관리가 모두 한 파일에 있다.

**분리 대상:**

| 파일 | 내용 | 근거 |
|------|------|------|
| `octovault_controller.go` | Reconcile, SetupWithManager, ensurePendingInit | 컨트롤러 진입점만 유지 |
| `octovault_apply.go` | applyConfigMap, applySecret, applyOutput | 리소스 적용 로직 분리 |
| `octovault_fetch.go` | loadRepoAndToken, tryFetch, tryValidate, parseAndResolveType | 데이터 로딩/파싱 분리 |
| `octovault_status.go` | setSyncedStatus, ensurePendingInit, updateStatusIfChanged, fail, statusEqualOV | 상태 관리 분리 |
| `octovault_finalizer.go` | orphanTargets, finalizer 관련 | 삭제 처리 분리 |
| `helpers.go` | parseDurationOr, normalizeRepoName, shortSHA, sha256OfStringMap, sha256OfBytesMap, equalStringMap, equalBytesMap, getFromSecret, summarizeExtRefs, labelSafe, setManagedLabels, upsertCond, upsertReadyCondition | 공용 유틸 분리 |

### S2. 중복 헬퍼 제거 및 통합

현재 발견된 중복:
- `getFromSecret` (octovault_controller.go:970) vs `orgFromSecret` (repo_secret_controller.go:88): 동일 로직이 다른 이름으로 존재
- `newScheme` (octovault_controller_test.go:66) vs `schemeForRepoTests` (octorepository_controller_test.go:32) vs `schemeForRepoSecretTests` (repo_secret_controller_test.go:26): 동일 스킴 생성 로직 3회 중복
- `newFakeClient` (octovault_controller_test.go:74) vs `fakeClientRepo` (octorepository_controller_test.go:40): 유사 로직
- `upsertCond` (octovault_controller.go:790) vs `upsertReadyCondition` (octorepository_controller.go:407): 기능 중복 (Ready 타입 하드코딩 여부만 차이)
- `statusEqualOV` (octovault_controller.go:815) vs `statusEqual` (octorepository_controller.go:434): 유사 패턴
- `maxWorkers()` 메서드가 3개 컨트롤러에 각각 동일하게 존재

### S3. OctoRepositoryReconciler에서 직접 HTTP 호출 제거

`octorepository_controller.go`의 `checkOwnerAccess` → `probeList`가 `http.DefaultClient`를 직접 사용하여 GitHub API를 호출한다.

- `OrgAccessChecker` 인터페이스가 이미 `org_checker.go`에 선언되어 있으나 **사용되지 않고 있다**
- `Checker OrgAccessChecker` 필드가 `OctoRepositoryReconciler`에 있으나 `checkOwnerAccess`에서 `r.Checker`를 사용하지 않고 직접 HTTP 호출
- 리팩토링: `checkOwnerAccess` 로직을 `OrgAccessChecker` 구현체로 이동, `Reconcile`에서 `r.Checker.Check()` 사용

### S4. valuesDoc 모델 패키지 분리

`valuesDoc` 구조체가 `controller` 패키지 안에 선언되어 있다. 이것은 도메인 모델이므로 별도 패키지 또는 `api` 패키지에 위치하는 것이 적절하다.

### S5. 상수/라벨 일관성 정리

현재 상수 정의가 여러 파일에 분산:
- `octovault_controller.go`: `CondReady`, `LabelManagedBy`, `LabelOVOwnerNS`, `LabelOVOwnerName`, `AnnoOVOwnerFull`, `AnnoOVRetainedBy`, `FinalizerOV`
- `repo_secret_controller.go`: `LabelRepo`, `AnnOrganization`
- `octorepository_controller.go`: `LabelRepoTrue`
- 또한 `applyConfigMap`과 `applySecret` 내부에서 `"reconcile.octovault.it/managed-by"` 등의 하드코딩된 라벨이 상수화되지 않음

## Alternative Solutions

### A1. 파일 분리 없이 함수 그룹핑만 정리
- 장점: 파일 수 변경 없음
- 단점: 1057줄 파일 유지, 코드 리뷰/네비게이션 어려움

### A2. 컨트롤러를 완전히 새 패키지로 분리 (예: `internal/reconciler/octovault/`, `internal/reconciler/octorepository/`)
- 장점: 완전한 패키지 격리
- 단점: 과도한 구조 변경, 공유 헬퍼 접근 문제, import cycle 위험

### A3. 도메인 서비스 레이어 추가 (예: `internal/service/`)
- 장점: 비즈니스 로직과 컨트롤러 로직 완전 분리
- 단점: 현재 규모 대비 과도한 추상화

## Exceptions

1. **GitHub API 실패**: 404, 401, 403, 429, 500+ → Fail 상태 + RequeueAfter
2. **AWS SM/PS 실패**: ResourceNotFoundException, DecryptionFailure, InvalidRequest → Fail 상태
3. **values.yaml 파싱 실패**: YAML 구문 오류, metadata.type 누락/잘못된 값
4. **data.key 비어있음**: 빈 키 검증 → Fail
5. **OctoRepository 미존재**: NotFound → Fail + Requeue
6. **Secret 미존재 또는 password 키 누락**: Fail + Requeue
7. **base64 디코딩 실패**: passwordEncoding=base64일 때 잘못된 값
8. **AwsSM/AwsPS provider nil**: 환경 미설정 시
9. **jsonKey 추출 실패**: JSON 파싱 오류, 경로 미존재

## 비기능 요구사항

1. **리팩토링은 기존 동작을 변경하지 않아야 한다** - 모든 기존 테스트가 통과해야 함
2. **코드 커버리지 유지/향상** - 리팩토링으로 테스트 불가 코드가 생기면 안 됨
3. **점진적 리팩토링** - 한 번에 모든 것을 바꾸지 않고 단계별 진행
4. **빌드 성공 보장** - 각 리팩토링 단계마다 `go build ./...`, `go test ./...` 통과

## Constraints

1. Kubebuilder 기반 프로젝트 구조 유지 (`api/`, `internal/controller/`, `cmd/`)
2. `controller-runtime` 프레임워크 규약 준수 (Reconcile 시그니처, SetupWithManager 등)
3. 기존 CRD 스키마는 변경하지 않음
4. Go 1.24 호환
5. CLAUDE.md의 TDD 규칙 준수
6. Functional Options Pattern (인자 3개 초과 시)
7. 상수는 PascalCase

## External Infrastructure Services

1. **GitHub REST API** (api.github.com) - 파일 내용, 스키마, 커밋 SHA 조회
2. **AWS Secrets Manager** - 외부 시크릿 값 조회 + JSON 키 추출
3. **AWS Systems Manager Parameter Store** - 파라미터 값 조회 + JSON 키 추출
4. **Kubernetes API Server** - CR, Secret, ConfigMap CRUD
